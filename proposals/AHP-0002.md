## Summary

This non-normative design record accompanies optional `transport.headers` in the
draft registration spec/schema and coordinated TypeScript, Python, Go, and Rust
implementations. It remains Draft, not formally accepted or released.

The authoritative contract is [AHP-REG-003](../spec/draft/base/registration.md#AHP-REG-003).
The design permits ordinary HTTP configuration rather than adding a separate
AHP header policy: all valid names, literal credentials, native value validation,
configured-last precedence, and backend-wide event/upload support.

## Motivation

Backends and gateways need portable custom metadata and credentials without
requiring lower-level HTTP-client customization. The registration path must carry
the same configuration through actual event delivery and content uploads.

## Design

- Values remain `string | {valueEnv: string} | {valueRef: string}`. Unknown source
  fields are ignored; exactly one recognized source is required.
- Literal API keys, cookies, and `Authorization: Bearer abc123` are allowed.
  Strings are not interpolated and references resolve complete header values.
- Reuse existing environment/secret helpers, deadlines, cancellation, and redacted
  errors. Do not introduce an independent secret-resolution framework.
- Allow every valid HTTP field name, including authentication, browser, protocol,
  and default names. No denylist, ASCII-only value restriction, or new size policy.
  Native HTTP validation rejects injection (CR/LF/NUL) and governs other values;
  legal non-ASCII is accepted where supported by the native library.
- Compare names case-insensitively. The last property in configuration iteration
  order wins; deduplicate before resolution. Parsers must preserve that order.
- Build transport/default/authentication headers first, then apply configured
  values LAST, including `Authorization` and `Content-Type` overrides.
- Configured Authorization in any casing and with any source suppresses OAuth
  discovery, acquisition, challenge handling, and retries, even alongside auth
  configuration. Resolve it normally; failures do not fall back to OAuth.
- Apply the same backend configuration to events AND content uploads, using the
  upload operation's existing budget/helpers and configured-last merging. Explicit
  Authorization suppresses upload OAuth as well.
- Preserve existing redirect behavior and native sensitive-header handling. Do
  not introduce blanket forwarding or a new redirect prohibition.
- Do not install these headers globally or send them to unrelated backends or
  discovery/token endpoints. Existing diagnostic redaction applies to all values.

## Schema and conformance

The draft schema defines stable `HttpHeaderSource` and `HttpHeaderValue` models
for all four canonical generators. String values have no ASCII restriction;
CR/LF/NUL injection is rejected. Shared fixtures cover valid literal credentials,
non-ASCII configuration, duplicates, sources, and malformed shapes. HTTP profile
runtime evidence covers actual event/upload requests, last-wins/default overrides,
OAuth suppression, existing redirects, secret handling, and redaction. Schema
acceptance alone cannot establish runtime header support.

## Compatibility and security

This is additive registration configuration, not a new event-envelope field.
Older implementations may ignore it; deployments must select supporting SDKs.
Configured credentials are trusted configuration and must be protected accordingly.
The receiver remains responsible for authenticating/authorizing the resulting
request. Native stacks may reject unsupported headers or values; report that
failure rather than silently dropping configuration. No new transport limits,
retry mechanism, credential negotiation, or stdio behavior is introduced.

## Alternatives and references

Programmatic-only headers do not reliably reach registered delivery and uploads.
A reserved-name policy or authentication-owned final merge would prevent explicit
user overrides and is not this design. The earlier restricted proposal is
superseded by the configured-last, native-HTTP contract described here.
MCP client configuration and transport implementations are references, not a wire
dependency or a universal configuration standard. Their precedence choices do not
override the AHP contract. Pinned MIT-licensed sources are linked below; no upstream
implementation code is copied.

## Rollout and decision record

PR #41 contains the draft spec/schema/fixtures and canonical model metadata.
TypeScript SDK PR #38, Python SDK PR #41, Go SDK PR #39, and Rust SDK PR #44 carry
the runtime implementations and regenerate models from this protocol snapshot.
Temporary proposed SDK revision pins coordinate integration, then must be removed
for a fresh default-main run after the dependencies land. No merge or release is
implied; formal acceptance remains pending. AHP-0002 is already assigned.
