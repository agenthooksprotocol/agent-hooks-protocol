# AHP-0002: HTTP registration headers across the spec and SDKs

## Summary

Add `transport.headers` to HTTP backend registration in the spec and the
TypeScript, Python, Go, and Rust SDKs. Configured headers apply to event requests
and content uploads.

[AHP-REG-003](../spec/draft/base/registration.md#AHP-REG-003) defines the requirements.

## Motivation

Backends and gateways need custom metadata and credentials. Configuring these in
`hooks.json` avoids separate HTTP-client setup in each SDK.

## Design

### Header values

Each value is a string, `{ "valueEnv": "NAME" }`, or
`{ "valueRef": "reference" }`. Source objects require exactly one recognized
source; unknown fields are ignored.

Literal credentials are allowed, including API keys, cookies, and
`Authorization: Bearer abc123`. Strings are not interpolated. References resolve
the complete header value.

Resolution uses existing environment and secret helpers, operation deadlines,
cancellation, and error redaction.

### HTTP validation

Any valid HTTP field name can be configured. The HTTP library validates values,
including rejection of CR, LF, and NUL. Non-ASCII values are allowed where the
library supports them. Unsupported names or values cause an error; they are not
silently dropped.

### Precedence and authentication

Names are case-insensitive. When names repeat with different casing, the last
property in configuration order wins. Parsers preserve this order. Deduplication
occurs before secret resolution.

Configured headers override transport defaults and authentication headers,
including `Authorization` and `Content-Type`.

A configured `Authorization` header suppresses OAuth discovery, token acquisition,
challenge handling, and OAuth retries. This applies to every casing and value
source, even when authentication is also configured. Resolution failures do not
fall back to OAuth.

### Request scope

The same backend headers apply to events and content uploads. Uploads use their
existing operation deadlines and secret helpers. Configured `Authorization` also
suppresses upload OAuth.

Redirect behavior and the HTTP library's handling of sensitive headers remain
unchanged. Headers are not installed as global client defaults or sent to unrelated
backends, discovery endpoints, or token endpoints. All configured values are
redacted from diagnostics.

## Schema and conformance

The registration schema defines `HttpHeaderSource` and `HttpHeaderValue` for the
four SDK generators. Shared fixtures cover literal credentials, non-ASCII values,
duplicate names, secret sources, and invalid configuration shapes.

Runtime tests cover event and upload requests, header precedence, OAuth suppression,
redirects, secret resolution, and redaction. Schema validation alone does not
establish runtime support.

## Compatibility and security

`transport.headers` is an optional registration field. It does not change event
envelopes or stdio behavior. Older SDKs may ignore it; deployments that require
headers must use a supporting SDK version.

Configuration can contain credentials and must be protected. Servers remain
responsible for authenticating and authorizing requests. Existing transport limits
and retry behavior remain unchanged.

## MCP references

VS Code supports headers in MCP client configuration. The MCP TypeScript and Python
SDKs support custom HTTP request headers. These are client configuration features,
not a common configuration format defined by the MCP wire protocol.
